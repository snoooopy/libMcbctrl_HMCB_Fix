# V2.0.1.1 接收/解析解耦移植（libMcbctrl）

- 日期：2026-10-20
- 参考源码：`HMCB-H_DLL_TEST V2.0.1.1_20261012_HMCB4/MCBCtrl`（新 Windows 库）
- 基线：本仓库 `v1.1` 标签（对应旧版 `V1.4.2.4_20260319` 行为）
- 目标：按新版 Windows 源码，把 HMCB4 数据路径从"接收+解析一体"改造为
  "接收线程只收字节入共享缓冲 + 每 MCB 独立解析线程"，提高传输吞吐。

## 1. 新版 Windows 库改了什么（V1.4.2.4 → V2.0.1.1 diff 结论）

应用层（TEST）无实质变化；改动集中在库：

| 文件 | 改动 |
|---|---|
| `MCBDataBuffer.h`（新增） | 线性缓冲 `CMCBDataBuffer`：读指针消费 O(1)、惰性压缩、`Data()` 零拷贝指针、`PushFront/EraseAt` 容错 |
| `MCBCtrlC.h` | 新增 `MCBParseContext`（共享缓冲 local/hDataEvent/解析线程/统计）与 `MCBParseThreadProc / StartParseThreads / StopParseThreads / ParseBuffer_HMCB4` |
| `MCBCtrlC_HMCB4.cpp` | `FetchMsg_HMCB4` 只做 recv+Append+SetEvent；原 `ETH_read_and_parse_dataEx_Thread_HMCB4` 整体退役；解析改为 `ParseBuffer_HMCB4`（指针式解析，缺 0xAA 容错、DB/CB 前多 1 字节容错、半包等待） |
| 生命周期 | `Start_HMCB4` 置 m_bStart 后 `StartParseThreads()`；`NormalEndDAQ / CheckDataEnd / CloseMCB` 在 `m_bStart=0` 后 `StopParseThreads()`（数据消费完再停线程） |
| 线程安全加固 | 跨线程标志 bool/int → `volatile LONG` + `AtomicLoadL/StoreL/OrL/AndL`（type_def.h） |
| 其他 | `WriteLogFile` 加 `bFlush` 参数（高频路径免每行 flush）；`m_MCBDataTmp` 改 per-MCB 数组；FX64 芯片型号支持（超范围，未移植） |

## 2. Linux 移植对照表

| Windows | Linux 实现 |
|---|---|
| `CreateEvent(NULL,TRUE,FALSE,NULL)` 手动重置事件 | `MCBCtrlC::ManualResetEvent`（mutex+condition_variable+signaled，`wait(100)` 带超时） |
| `CRITICAL_SECTION csBuf` | `std::mutex csBuf`（每 MCB 一把） |
| `CreateThread` / `WaitForSingleObject` / `TerminateThread 兜底` | `std::thread` + 完成标志 `bThreadDone`+`doneCv` 限时等待（5s+10s 两段），超时 `detach` 养老（绝不强杀） |
| `Interlocked*` 原子操作 | GCC `__atomic_*` 内建（`type_def.h` 尾部 `AtomicLoadL/StoreL/OrL/AndL/TestBitL`，`MCB_LONG=long`） |
| `GetTickCount()` | `NucTool::GetTickCount()`（既有） |
| `BOOL/TRUE/FALSE`（Linux 缺失） | `replenish_type.hpp` 补 `typedef int BOOL;` + TRUE/FALSE 宏 |
| `SYS_gettid` | `#include <sys/syscall.h>`（Linux 分支） |

**共享缓冲落点**：Windows 新版保留旧全局 `glb_data_buf_vetor[]` 改型为
`CMCBDataBuffer`；Linux 版为避免非 HMCB4 老路径回归，**不动旧全局 vector**，
把共享缓冲放进 `MCBParseContext::shared`（数据流与 Windows 完全一致：
recv→shared→local→解析）。

## 4. 移植中发现并修复的关键差异

### 4.1 半包等待必须在"形状校验"之后（移植缺陷，真机抓出）

V2.0.1.1 的 `ParseBuffer_HMCB4` 在**引导码校验之前**做
`SC_pkg_len > avail → return true（等数据）`。字节错位时垃圾字节会被当作
长度字段（<16MB 合法区间但 >avail），解析器进入"等半包"死等（实测真机
73KB/s 需等数分钟），表现为采集约 1 秒后数据流完全停滞、local 无限增长。
旧版 V1.4.2.4 因逐字节跳过重同步无此问题。

修复：调整校验顺序为 **DBLine 合法 → 长度上限 → 引导码（缺 AA 补齐/跳字节）
→ 类型/长度匹配（DB/CB 前多 1 字节容错）→ 才允许 `len>avail` 等半包**。
形状非法的字节一律 1 字节/次重同步，绝不基于未校验的长度等待。
（该顺序问题Windows 版同样存在，属 V2.0.1.1 潜在缺陷，Linux 版先行修复。）

### 4.2 StopParseThreads 并发防护

`StopParseThreads` 可由定时线程（CheckDataEnd）与命令线程（NormalEndDAQ/
CloseMCB）并发进入，`std::thread::join` 并发调用是 UB。加函数级静态互斥
（Start/Stop 共用一把）。Windows 句柄模型天然可重入，移植必须显式防护。

### 4.3 m_MCBDataTmp per-MCB（记录为已知差异）

V2 把 `m_MCBDataTmp` 改为 `per-MCB 数组`；本机现网单板运行、且 ZeroPadding
路径只在解析线程执行，暂未移植该改动（避免大范围触碰 UpdateOnePacketDataToApp），
多板（MCBNUM>1）部署前需补。

## 5. 诊断钩子（保留）

- 环境变量 `HMCB_LIB_DEBUG=1`：接收侧每秒打印 `cnt/bytes/start/stop`；
  解析侧每秒打印 `rate/shared/local/start/stop/bStop`。
  本次停滞 bug 即由此定位（recv 正常 250 包/s，parse rate=0 且 local 线性增长）。
- 日志新增线程生命周期行：`parse thread created/started/exit. recv=…, parsed=…`。

## 6. 真机验证（CX1664DE @192.111.111.211，HMCB4 模式，1DM×64×2×16bit）

| 项 | 结果 |

### 排障记录（供后续参考）

1. 现象：v2 库采集 ~1s 后数据停止、GUI 计数冻结。
2. 排除设备：git 标签重建 v1.1 原库同环境 250fps 正常。
3. 定位：`HMCB_LIB_DEBUG=1` 显示 recv 正常、parse rate=0 且 local 线性增长
   → 解析器卡在 `SC_pkg_len > avail` 的半包等待（未校验的垃圾长度字段）。
4. 修复：校验顺序重排（§4.1），复测通过。
5. 另注意：测试进程必须 `pkill -x HMCB_Qt` 并确认 `ss -tn` 无残留连接——
   设备为单会话 TCP，孤儿进程会占住会话槽导致后续连接全部
   `socket failed`（本次排障中曾误判为设备掉线）。
