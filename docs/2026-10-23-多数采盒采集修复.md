# 多数采盒采集修复（真机三盒验收）

- 日期：2026-10-23
- 配置：`HMCB-H_DLL_TEST V2.0.1.1_20261010/MCBCtrl.ini`（MCBNUM=3，每盒 16DM=4DBLine×4DM，
  ROW=64×COLUMN=8，ADBIT=20，数据发生器 bin `HMCB_CT_DATA_GEN_FPGA_TOP.bin`，INTT=200us）
- 真机：192.111.111.211/212/213 三盒，Windows V2.0.1.1 同配置三盒 1250fps 同步为对照基线

## 1. 症状

- 单盒采集正常；两盒以上数据异常（历史版本：双盒反复"DM 数量自检失败→无限重连"）。
- 本轮 v2.0 库真机：三盒"轮流"收数（各收几秒停，板 2 永远 0 帧），无法并行。

## 2. 根因（两个独立缺陷叠加）

### 2.1 陈年越界 bug：gbl_DBLine_Size 定义/声明不匹配（多板必现）

- `CB_bsp.cpp` 定义 `INT32U gbl_DBLine_Size[MAX_MCBNUM]`（**一维**，32B），
  而全部使用处 extern 为 `[MAX_MCBNUM][MAX_DBLINENUM]`（二维，128B）。
- 单盒只访问线性偏移 0..3，恰在一维界内 → **单盒永远正常**（此 bug 长期潜伏）。
- 三板访问 `[2][0..3]`=偏移 8..11 → **越界读相邻全局变量** → `gbl_DBLine_Size[2][*]`
  = 0xFFFFFFFF → 解析线程 `minSize=UINT_MAX` → `avail < minSize` 永真 →
  永远走"等半包"分支 → 板 2 local 缓冲 21MB+ 暴涨、0 包上送（真机诊断实锤）。
- **Windows V2 定义就是二维**（CB_bsp.cpp:118），Linux 移植时抄错。
- 修复：定义对齐为二维。

### 2.2 接收侧内核缓冲不足（高帧率多盒轮流反压）

- 每盒 16DM@1250fps ≈ 26MB/s；`ss -tnm` 实测数据口接收缓冲仅 131~338KB
  （TCP autotune 稳态在低水位），接收调度稍有抖动即内核缓冲溢出 →
  设备 TCP 窗口反压 → 多盒呈轮流独占。
- 修复：① 单次接收缓冲 `SOCKETBUFSIZE` 5760→64KB（一次事件尽量取空内核缓冲）；
  ② Connect 后显式 `SO_RCVBUF=4MB`（rmem_max=4MB 内全额生效）。
  实测 ① 即消除轮流；② 为抖动保险。

### 2.3 多板并发撕裂隐患：m_MCBDataTmp per-MCB（v2.0 移植已知项补齐）

- `m_MCBDataTmp`（ZeroPadding 补帧/通道调整的临时区）原为 static 单实例，
  多板解析线程并发写 → 帧数据撕裂。Windows V2 已改 per-MCB 数组。
- 修复：`m_MCBDataTmp[MAX_MCBNUM]`，使用点按板索引（含回调传址
  `gCallBack(MCB_MSG_DATA, WPARAM(&m_MCBDataTmp[nMCB]), nMCB)`——该处漏改
  会让多板回调全部指向同一地址，为本次修复的关键点）。

### 2.4 历史双盒"无限重连"解释（配置层）

旧版 Release 包日志（`HMCB_Qt_Release_20260921`）的双盒失败是配置错误所致：
`MCB0DB0ADNUM  4` **缺 `=`** → 库取缺省值=DB0=整板总数(8) → 与设备自检 (4,4)
不符 → 反复"Detector module overflow"重连；`MCBNUM` 当时写 3 又多连不存在的
.213。当前参考配置无此问题（`//` 注释、键后空格、CRLF 均已验证解析安全）。

## 3. 应用层（HMCB_Qt）配套修改

- `onDeviceReady`：DVREADY 为库级全局状态，所有在线板统一点亮 READY
  （原来只亮板 0）。
- `m_lastSC/PC/DI` 按板数组化：1Hz tick 分板刷新侧栏 SOCKET/PULSE
  （原来多板混用板 0 变量）。
- 速度统计以板 0 scounter 为基准（对照 Windows m_MCBScount[m_nMCB]）。
- `config/MCBCtrl.ini` + 数据发生器 bin：部署 V2.0.1.1_20261010 参考配置
  （三盒），单盒旧配置备份于库仓文档。

## 7. 追加修复：通道排布改为模块优先（数据视图修正，2026-10-23）

### 7.1 现象

三盒并行后网格数据视图错误：相邻 ADM 列成对重复（ADM00/01 都显示 0..63、
ADM02/03 都显示 64..127……），ExDATA 列"消失"。

### 7.2 根因

组装循环为**列优先**（`nCh = col*nDMNum*nRow + dm*nRow + row`，沿袭
Windows 源码），把"同一逻辑通道在不同模块槽的镜像"铺满线性流——真机
数据发生器实测：通道值仅由 (列,行) 决定（值=col*64+row），与模块槽无关
（发生器把同一组 0..nCol*nRow-1 连续计数广播到所有模块槽）。列优先布局下
任何单个模块的 512 通道被拆散到流中 8 个 1024 段，网格/保存均无法呈现
"每模块 0..511 连续"的模块视图。

### 7.3 修复

组装循环改**模块（ADM/DM 槽）优先**：
`nCh = dm*nColNum*nRowNum + col*nRowNum + row`。

- 每模块槽内通道连续：addata[dm*512 + col*64 + row] = col*64 + row
  → 每列（ADM）竖读 **0..511 连续**，全部模块列相同（发生器广播语义）。
- 单盒（nDMNum=1）两种顺序数学恒等，无回归。
- ExDATA 未丢失：ExDATA 列按 MFC 语义始终在**最后一页尾列**
  （16ADM+ExDATA=17 列 → 页 2 第 7 列；单盒时在页 1），值源为帧头
  ain0/ptsm（前 5 行），Qt/Windows 行为一致。

### 7.4 验证（真机三盒）

- 全帧分析：16 个 512 通道块全部为"起点 0、长度 512"的连续 +1 段。
- 网格：ADM00-09 列竖读 0,1,2,...（0..511 连续），行标 CH0-00..CH7-63；
  4027 fps / 82.3 MB/s；ctest 14/14（含 ExDATA 页尾列/前 5 行用例）。
